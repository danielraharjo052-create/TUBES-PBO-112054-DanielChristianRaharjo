# ConcertHub - Update Role, Register, Ticket, and Transaction Flow

## Role differences
- ADMIN: can add and delete concerts, view all transactions, view accounts, and create STAFF accounts.
- STAFF: can view concerts and all customer transactions, then verify payments marked as `DIBAYAR`. STAFF cannot add/delete concerts or create accounts.
- CUSTOMER: can register from the login page, browse tickets, book tickets, see only their own transaction history, and mark their own transaction as `DIBAYAR` after the simulated payment.

## Demo accounts
- `admin` / `admin123`
- `staff` / `staff123`
- `customer` / `customer123`

New public registrations always receive the `CUSTOMER` role. The database stores only username, password hash, and role, so the registration form asks for username, password, and password confirmation.

## Database
Run `sql/schema.sql` against the PostgreSQL database used by the application. It creates/updates the transaction status constraint to support:
- `PENDING`: booking created; ticket quota has been reduced.
- `DIBAYAR`: customer marked the simulated payment as paid.
- `SUKSES`: staff verified the payment.

Transaction history is isolated by `transactions.user_id`; each customer sees only their own rows. STAFF and ADMIN can view all transactions.

## Run on Windows
Open a terminal in the project root (the folder containing `gradlew.bat`):

```powershell
.\gradlew.bat clean
.\gradlew.bat build
.\gradlew.bat run
```

Update database credentials in `app/src/main/java/konser/config/AppConfig.java` if needed.

## Payment timeout (15 minutes)
- A new booking starts as `PENDING` and reserves ticket quota.
- If the customer does not mark it as paid within 15 minutes, the application changes it to `CANCELLED` and restores the exact quantity to the ticket quota.
- Expiration is checked every 30 seconds while the desktop app is open, and also whenever transaction history or booking/payment actions are requested. If the app is closed, expired orders are processed the next time it is opened.
- `CANCELLED` is terminal; the customer cannot pay an expired order. They must create a new booking.

## Important: update an existing database
If the database already existed before this update, run `sql/fix_transaction_status.sql` once in pgAdmin / DBeaver / psql. This migration replaces old transaction status CHECK constraints with the current allowed values (`PENDING`, `DIBAYAR`, `SUKSES`, `CANCELLED`). Do not rely only on `CREATE TABLE IF NOT EXISTS` to modify an existing table's constraints.

## Transaction IDs
Transaction IDs are generated by one database-wide sequence and will keep increasing across all customers. This is correct for a primary key: IDs must be unique across the entire `transactions` table. Customer transaction history remains separate because each row has its own `user_id`.
